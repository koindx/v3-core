# KoinDX v3 Core

Port of [Uniswap v3 core](https://github.com/Uniswap/v3-core) to Koinos (AssemblyScript):
concentrated liquidity pools and the factory that deploys them, like
[KoinDX v2 core](https://github.com/koindx/v2-core) for Uniswap v2.

| Contract | Uniswap v3 | Description |
|---|---|---|
| `factory` | `UniswapV3Factory` | registry of pools, fee tiers (100/1, 500/10, 3000/60, 10000/200), owner |
| `pool` | `UniswapV3Pool` | swaps, positions, fees, protocol fees, flash loans and the oracle |

| Library | Uniswap v3 |
|---|---|
| `libraries/U256.ts`, `libraries/I256.ts` | `uint256`/`int256`, `FullMath` (512-bit `mulDiv`), `UnsafeMath`, `BitMath` |
| `libraries/TickMath.ts` | `TickMath` |
| `libraries/SqrtPriceMath.ts` | `SqrtPriceMath` |
| `libraries/SwapMath.ts` | `SwapMath` |
| `libraries/LiquidityMath.ts`, `libraries/SafeCast.ts`, `libraries/FixedPoint.ts` | `LiquidityMath`, `SafeCast`, `FixedPoint96`, `FixedPoint128` |
| `contracts/pool/assembly/libraries/*` | `Tick`, `TickBitmap`, `Position`, `Oracle` |

`U256` is checked by default (reverts on overflow, like Solidity 0.8) and only the values that
Uniswap intentionally lets wrap around use the explicit wrapping operations. See
[docs/OVERFLOW.md](docs/OVERFLOW.md).

## Requirements

Node.js 18+ and yarn 1. The toolchain is pinned in `package.json` (AssemblyScript 0.19.23,
`@koinos/sdk-as` 1.0.2, `@koinos/as-proto-gen` 1.0.3, `@koinos/abi-proto-gen` 1.0.0,
`@koinos/as-gen` 1.0.0), same as the KoinDX v2 contracts.

```sh
yarn install
```

## Build

Every contract is built separately, like the KoinDX v2 contracts (`yarn build:release`):

| Contract | Release build (deployed) | Debug build | Output |
|---|---|---|---|
| pool | `yarn build:release:pool` | `yarn build:debug:pool` | `contracts/pool/build/<mode>/contract.wasm`, `contracts/pool/abi/` |
| factory | `yarn build:release:factory` | `yarn build:debug:factory` | `contracts/factory/build/<mode>/contract.wasm`, `contracts/factory/abi/` |

`yarn build:release` and `yarn build:debug` build both. The factory embeds the hash of the pool
bytecode, so building the factory builds the pool first (its hash is always the one of the
current pool sources).

`scripts/build.js` does what `koinos-sdk-as-cli build-all` does for each contract (ABI with the
`authorize` entry point, protobuf classes, `index.ts` dispatcher, wasm), plus:

- the contracts are compiled with the AssemblyScript **`stub` runtime** (no garbage collector,
  memory is released when the call ends). The incremental GC of AssemblyScript 0.19 freed live
  objects in some calls (corrupted values returned after a tick crossing swap); without GC that
  can't happen, and running out of memory (Koinos allows 32 MiB per call) would only revert.
- the **pool bytecode hash** (sha256 multihash) is written to
  `contracts/factory/assembly/PoolHash.ts` before compiling the factory (like the hash of the
  pair in the constants of the v2 periphery, but generated). `yarn hash` prints it.
- repeated numeric proto fields must be `[packed = true]`, and the packed decoders generated by
  as-proto-gen are patched (they drop the last element of an array when it is a one byte varint).
- `DEBUG_ABORT=1 yarn build:release` replaces the opaque `module exited due to trap` of the
  AssemblyScript runtime errors with a revert that includes the message and source location
  (`utils/Abort.ts`). Only for local debugging: the deployment scripts refuse these builds.

## Test

```sh
yarn test
```

The math libraries are compiled to a test harness (`tests/harness/index.ts`) and compared
(differential testing) against a BigInt transliteration of the Solidity code
(`tests/reference.js`) and the official `@uniswap/v3-sdk`: random inputs including edge values,
Uniswap test vectors, Knuth division add-back cases and the Koinos amount limits. `U256` also
passes the test vectors of the audited [as-bignum](https://github.com/btc-vision/as-bignum)
library and the cases of its audit report (`tests/as-bignum.test.js`).
`FUZZ_RUNS=20000 yarn test` runs more random cases.

All the test suites of Uniswap v3-core are ported (`tests/uniswap`) and run against the compiled
contracts in an emulator of the Koinos VM (`tests/vm`), with the expected values of Uniswap. A
differential fuzzer compares random sequences of operations with the Uniswap v3 bytecode run in an
EVM. See [docs/UNISWAP_TESTS.md](docs/UNISWAP_TESTS.md). `tests/koinos-security.test.js` covers the
attacks specific to Koinos, see the [security review](SECURITY.md).

End to end tests of the contracts on a local Koinos node are in the
[integration tests](https://github.com/koindx/v3-integration-tests).

## Deployment

### Factory

```sh
yarn build:release
PRIVATE_KEY=<wif of the factory account> RPC_URL=<rpc url> yarn deploy:factory
```

The factory is uploaded overriding `authorizes_upload_contract`, so its code can't be changed.
The factory account is the initial owner (`set_owner`, `enable_fee_amount`, protocol fees of
the pools); the ownership can be transferred later, e.g. to a governance contract, in two steps:
`set_owner` proposes the new owner, which calls `accept_owner` (a proposal to a wrong address
doesn't lock the owner functions).

The owner also exempts the tokens that have no allowances (no `approve`, e.g. KCS-1 tokens) from
the allowance check of `create_pool` (see below): `set_allowances_exempt({ token, exempt })`. Only
exempt a token after checking it has no allowances at all.

Set the factory address in `networks.json` of [v3-periphery](https://github.com/koindx/v3-periphery) before building it.

### Pools

Koinos has no `CREATE2`, so pools are created like the KoinDX v2 pairs: the pool bytecode is
uploaded to a new address **in the same transaction** that calls `factory.create_pool`, after the
upload. The factory checks that:

- `create_pool` is an operation of the transaction (not a call from a contract) and the upload
  comes before every call to the factory, so the pool code is installed when `configure` runs
  (SECURITY.md, finding F11);
- the transaction uploads exactly one contract, its bytecode hash is the pool hash embedded in
  the factory and it overrides `call_contract`, `transaction_application` and `upload_contract`
  (nobody, including the key of the new address, can act on behalf of the pool or upgrade it);
- the tokens are different, sorted by the factory, and the fee tier is enabled;
- `koin` and `vhp` are referenced by their name service name (not by address);
- the new address has no allowances on the two tokens (KCS-4 `get_allowances`): allowances granted
  with its key before the upload would let a spender move the tokens of the pool (finding F12). A
  token without allowances can't answer `get_allowances` (the creation reverts) until the owner
  exempts it.

Then the factory calls `pool.configure` once (factory, tokens, fee, tick spacing), which requires
an empty storage.

```sh
PRIVATE_KEY=<payer wif> RPC_URL=<rpc url> FACTORY=<factory address> \
TOKEN_A=koin TOKEN_B=<token address> FEE=3000 \
SQRT_PRICE_X96=79228162514264337593543950336 yarn create-pool
```

`SQRT_PRICE_X96` (optional) initializes the price in the same transaction
(`sqrt(token1 / token0) * 2^96`, 79228162514264337593543950336 = price 1). The periphery manager
also provides `initialize_pool_if_necessary` to create and initialize a pool from a dApp.

## Koinos specifics

| Uniswap v3 | KoinDX v3 |
|---|---|
| `msg.sender` | the calling contract (`System.getCaller`). `mint`/`swap`/`flash` must be called by a contract, which receives the callback |
| callbacks `uniswapV3MintCallback`... | entry points `koindx_v3_mint_callback` (0x7c878d25), `koindx_v3_swap_callback` (0x38e03f68), `koindx_v3_flash_callback` (0xcd7ce544) |
| `burn`/`collect` by `msg.sender` | position of the calling contract, or of `owner` (must authorize the transaction) when called directly |
| balances checked after the callback | same, with the `balance_of`/`transfer` entry points of the token contracts |
| `uint256` amounts | `u64` token amounts, like the Koinos tokens (`SafeCast` reverts instead of truncating) |
| `swap(recipient, zeroForOne, int256 amountSpecified, ...)` returns signed `amount0` / `amount1` | `swap(recipient, zero_for_one, exact_input, amount_specified: u64, ...)` returns `amount_in` / `amount_out` (u64), the same in `koindx_v3_swap_callback`, `quote_swap` and `swap_event`: any amount of a Koinos token can be swapped |
| `block.timestamp` | block timestamp in seconds (`header.timestamp / 1000`) truncated to 32 bits like Uniswap |
| view functions | read-only entry points; `get_populated_ticks` (TickLens) and `quote_swap` (quoter) added |

Big numbers (`sqrtPriceX96`, liquidity, fee growth...) are decimal strings in the ABI and compact
big endian bytes in storage.

### Limits

Measured on a local node (integration tests): a swap through an empty region of the tick bitmap
costs ~26k compute per bitmap word (256 ticks × tick spacing). The worst case, a swap across the
whole price range of a tick spacing 1 pool (3465 words), succeeds in one transaction with ~91M
compute. Read-only calls have a lower compute limit, so `quote_swap` (and the quoter) can
simulate swaps of a few hundred words: quotes of extreme swaps through empty ranges fail, the
swaps themselves don't. Memory (32 MiB per call) limits a swap to about 4600 initialized ticks
crossed; a swap through a denser region must be split.
